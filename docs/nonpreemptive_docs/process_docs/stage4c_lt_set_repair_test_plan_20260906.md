# Stage 4c：以 LT 为默认的多资源启动集合局部修正

日期：2026-09-06  
状态：待执行。依赖 [公共协议](stage4_lt_followup_test_protocol_20260906.md) 与 [结构诊断](stage4b_lt_failure_analysis_plan_20260906.md)，遵守 [4c 分纲](../plan_docs/stage4c_conflict_graph_packing.md)。

## 1. 主算法 C1

在每个多资源合法决策点，保留全部 active reservation，先用冻结 LT 构造默认新启动集合 S0。辅助算法只提出少量替代集合，经相同 LT 补全比较后决定是否修正。

首轮 work-conserving；使用正式 Cassini/Alibaba 同源配对及已有多资源手算/Exact 图。配对只支持受限机制研究，不当作多个独立拓扑验证样本。

## 2. 构造挑战集合

1. 过滤所有与 active 通信冲突的候选，构建剩余候选之间的固定资源冲突关系。
2. 从 S0 中找一个通信 A：至少阻挡两个彼此兼容的未选通信 B、C。开发首版按冻结 LT 顺序选第一个满足条件的 A，避免按已知收益选 A。
3. 排除 A，按 LT 在剩余可启动候选中重新构造完整集合 S1。
4. 按原 LT 顺序重新扫描包括 A 在内的所有候选，只要兼容就补入，直到原候选全集中无可添加通信。若 A 被重新加入或 S1=S0，去重后跳过无效挑战。
5. 主版只比较 S0、S1；扩展版最多排除 S0 前两个符合条件的通信，各构造一个挑战，总候选不超过3。

第4步保证对原候选全集的极大性，不能只对“删掉 A 后的子图”验证 work-conserving。不枚举 ready 集的完整幂集。候选截断和遗漏范围必须记录。

## 3. 评分与持续执行

主评分为 Q_LT(s,S)，保留 S0，严格更好才换 S。集合内通信提交后持续运行；最早成员完成时，其他成员仍运行并保留资源，公共模拟器继续释放 compute/通信，剩余空闲资源按 LT 补全。不把集合当作必须同时完成的同步屏障。

快速筛选只用候选数量、冲突和资源脚印；LT tail 求和不得当成最终收益。若扩展低成本评分，分开比较简单加和与共享下游去重，只用于候选排序，再由完整补全确认。不能把资源并集大小直接解释为带宽或完成时间。

## 4. 可手算机制图

同一时刻有 A、B、C：
- A 占 r1+r2，通信10，后接 compute10。
- B 占 r1，通信2，后接 compute12。
- C 占 r2，通信2，后接 compute12。

若 tail 包含本节点，LT 先选 A（20>14），S0={A}，makespan24；先 S1={B,C} 再 A，makespan22。独立 Exact 核对两个模式，不用手算替代语义测试。

反例：A 后 compute30，B/C 后 compute1，其余不变。先 A 得40，先 B/C 得42。说明并行启动数量多不等于更好。

另加：外部 active 通信占 r1；B/C 时长不同；一个候选占三个资源；重新补全时 A 可重新加入；所有候选两两冲突；无集合分歧；共享后继只算一次；同刻完成与新 release。

## 5. optional-idle 扩展 C2

C1 完成后独立测试 C2：候选包含原 LT 动作、合法极大挑战，以及 S0 去掉 A 的合法非极大子集；仅在公共模拟器确认合法时加入空集 WAIT。非极大集合保留资源的价值仍由补全比较，不能人为延迟已选择成员。

需要区分“启动子集后在中间事件继续 LT”和“强制等到全体完成”，只允许前者。结果注明候选覆盖有限，不能推成 optional-idle 最优动作搜索。

## 6. 实验与代码边界

复用 src/llm_structured/nonpreemptive/packing/ 的 graph、constructors、features、policy；完整评估复用共享 runtime/rollout，不能复制第二套模拟器。离线审计/报告参考 stage4c_evaluate.py，先核对旧入口预算与当前 hash。

对照：FIFO 补全、LT 补全、job-aware LT、固定 job 顺序、C1、不做完整评估的直接局部替换（仅诊断）、同数随机合法集合挑战。消融排除1个/2个候选、候选生成与评估、简单加和/下游去重。同一个配对内固定 workload、arrival 和 DAG；route/resource/duration 的差异来自已验证拓扑转换。

报告有替换机会的状态比例、实际不同集合比例、条件修复比例、端到端改善、active 阻塞次数、集合生成时间、补全时间、fallback、内存、WAIT 和资源利用率。

## 7. 退出与交付

交付集合级决策日志、机制图、语义测试、两种模式独立表、配对分析及失败解释。若配对中有效但缺少新独立来源，只给配对内结论；需至少公共协议要求的独立来源验证后才讨论推广。

若冲突很多但有效集合差异很少、LT 已足够或评估太贵，形成受限/否定结论。不得为提高收益手改 route、资源或通信时长。
