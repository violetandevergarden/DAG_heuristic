# Stage 4d：Selective Rollout 研究规划

## 1. 阶段定位

本阶段研究如何只在真正值得前瞻的通信调度决策点使用 rollout，并把节省的搜索预算用于更宽的候选比较或更深的事件前瞻。基础策略是 Longest Tail；未触发、预算不足、搜索未完成或候选没有严格改善时，均回退到基础策略。

本阶段承接 Stage 4a 的真实 benchmark、Stage 4b 的结构观察和 Stage 4c 的多资源合法动作构造。研究重点不是证明已有 selective rollout 实现正确，也不是预设 selective rollout 一定优于全量 rollout，而是回答：

1. 哪些决策点存在真实且有后果的不确定性；
2. 哪些低成本信号能够识别这些决策点；
3. 在相同计算预算下，选择性前瞻能否取得比全量、周期或随机前瞻更好的质量与成本平衡；
4. 节省的预算用于增加候选宽度、前瞻深度或覆盖更多关键决策，哪种方式更有效。

现有触发器、特征、预算对象、实验脚本和历史小图结果仅作为待审查资产。本文先独立定义研究问题、实验方法和退出条件，不以现有代码行为限制规划。

## 2. 本阶段不处理的内容

本阶段不重新定义公共调度语义，也不处理：

- 主动 `WAIT`、不可抢占 communication 或按比例共享带宽；
- 算法自行推进时间、释放依赖或维护另一套剩余工作状态；
- 动态路由、迁移、部分资源获取或改变固定资源集合；
- 用 rollout 修改 compute 自动开始和不可抢占语义；
- 把 barrier 作为独立优先级替代 Longest Tail；
- 在本阶段同时优化 multi-job makespan、JCT、slowdown 和公平性；
- 用未完成搜索结果冒充精确估值或最优解；
- 把减少 rollout 调用次数本身视为调度质量改善。

多资源场景中的候选必须是 Stage 4c 定义的合法极大兼容集合。若 4c 尚未确定最终构造方法，本阶段先固定一种经过验证的简单构造，避免把 packing 改善误算成 rollout 收益。

## 3. 公共语义与搜索边界

所有 rollout 分支必须复用公共可抢占模拟器的状态转移：

- DAG 依赖是 finish-to-start；
- ready compute 自动开始、不可抢占并可并行；
- communication 只在离散调度事件处暂停和恢复，保留剩余工作；
- 有 eligible communication 时必须推进，不存在主动等待；
- 单 channel 动作选择一个 communication；
- 固定多资源动作选择资源兼容且 inclusion-maximal 的 communication 集合；
- 资源占用、任务完成、同刻事件闭包和 forced idle 都由模拟器处理。

算法只能选择合法动作，不得为搜索分支实现简化的时间推进。缓存、状态 key 或特征压缩不能丢失影响未来执行的信息；若只用于 heuristic 缓存，也必须验证启用和关闭缓存时动作及 makespan 一致。

基础优化目标为单 job makespan。以后扩展到 multi-job 时必须重新声明目标，不能直接复用本阶段结论。

## 4. 基本算法框架

在决策状态 $s$ 上，算法按以下顺序工作：

1. 公共模拟器给出合法动作集合或可构造的合法候选；
2. Longest Tail 产生基础动作 $a_{LT}$；
3. 计算低成本触发特征，判断当前是否值得 rollout；
4. 未触发时直接执行 $a_{LT}$；
5. 触发时，在明确预算内选择 challenger，并对候选动作进行有限前瞻；
6. 只有评价完整、结果可比较且候选严格优于基线时才改变动作；
7. 搜索未完成、超时、达到状态或调用上限时执行 $a_{LT}$，并记录 fallback 原因。

“严格优于”首先按声明的目标比较，再使用稳定、与答案无关的 tie-break。相同估值不应为了制造策略差异而切换动作。

Selective Rollout 包含两个彼此独立的研究组件：

- **触发器**：决定是否花费前瞻预算；
- **预算分配器**：决定触发后比较多少候选、前瞻多深以及何时停止。

二者必须分开消融。一个优秀触发器不等于候选评价正确，一个更深搜索的收益也不能自动归因于触发信号。

## 5. 决策点分类

并非所有存在多个 eligible communication 的状态都值得前瞻。正式统计至少区分：

- **无选择状态**：单 channel 只有一个合法通信，或多资源只有一个合法极大集合；
- **表面选择状态**：有多个合法动作，但它们在可验证范围内具有相同后续值；
- **策略分歧状态**：Longest Tail、FIFO、固定顺序或其他简单策略选择不同动作；
- **收益敏感状态**：不同首动作在 Exact 或受控评价下产生不同最终目标值；
- **基线错误状态**：Longest Tail 的动作不是最优首动作，或被可信有限前瞻严格改善；
- **未知状态**：因 Exact、完整候选评价或回放超时而无法判断。

触发器真正需要识别的是“基础策略可能出错且错误影响值得搜索成本”的状态，而不是所有 choice state。只报告 choice state 命中率会高估触发器价值。

## 6. Ground truth 与触发标签

### 6.1 小图精确标签

在 Exact 可完成的小图上，对每个被访问的决策状态枚举合法首动作，并用统一模拟器求其最优后续值。由此记录：

- 最优首动作集合；
- Longest Tail 是否属于最优首动作；
- 最优替代动作相对 Longest Tail 的目标改善；
- 首动作之间的最小非零差距；
- Exact 状态、状态数、时间和内存。

只有 Exact 完成并取得证书时，才能使用“基线错误”“最优首动作”等标签。time limit、state limit 或仅得到 feasible completion 的状态必须标为 unknown。

### 6.2 中大图代理标签

真实中大图通常没有 Exact。可以使用统一预算下的多候选 rollout、较高预算离线搜索、策略实际分歧和端到端反事实回放形成代理标签，但必须注明标签来源和上限。代理标签只能支持“在该评价器和预算下观察到改善”，不能称为最优或漏触发真值。

### 6.3 标签阈值

是否“值得触发”除质量差距外还应考虑搜索成本。可以预先定义最小有意义改善，例如绝对 makespan 差、相对差或完成关键事件的提前量；阈值必须在开发集确定，并报告不同阈值下的敏感性。

## 7. 候选触发信号

触发信号必须从当前只读 residual state 计算，且计算成本显著低于 rollout。候选分为以下几类。

### 7.1 选择不确定性

- eligible communication 或合法动作数量；
- Longest Tail 前两名或前两组动作的归一化分数差；
- FIFO、Longest Tail、固定顺序等低成本策略是否分歧；
- 多资源下冲突图密度、最大度、资源脚印大小和极大集合多样性；
- 当前继续原通信与切换通信是否给出不同动作。

分数差必须使用 residual tail，并处理零值、量纲和规模归一化。候选多并不必然表示选择重要，冲突密度高也不必然表示 Longest Tail 会出错。

### 7.2 立即释放影响

- 候选完成后是否立即释放 compute；
- 释放 compute 的工作量、持续时间或下游 tail；
- 是否完成 join 的最后一个未完成前驱；
- 是否释放新的 communication 或扩大后续选择空间；
- 多个候选是否共享相同后继，避免重复计数。

“可能释放”与“在当前剩余工作完成后立即释放”必须区分。原始 DAG 中存在后继，不等于本次动作能很快解锁它。

### 7.3 同步与训练结构

- 是否接近经 Stage 4b 验证的 join、iteration 或 pipeline 同步点；
- 候选是否属于不同 micro-batch、pipeline phase 或 collective role；
- 候选之间是否具有经过验证的重复或对称关系；
- 当前动作是否可能改变某个同步窗口的最后缺口。

这些结构信号只能作为 Longest Tail 不确定时的条件特征或触发信号。barrier 的具体评分与修正仍属于 Stage 4e。

### 7.4 资源与切换影响

- 候选使用的固定资源集合及热点资源差异；
- 一个大资源动作阻塞多个可兼容小动作的程度；
- 暂停当前未完成 communication 是否改变下一事件或竞争窗口；
- 预计增加的抢占和执行区间数。

资源负载只能作为候选信息，不能假设热点资源一定在最终关键路径。

### 7.5 触发器形式

按可解释性从低到高研究：

1. 仅在存在两个以上合法动作时触发；
2. 单一阈值，如 Longest Tail 分差小；
3. 两个条件的合取或析取，如“分差小且立即释放 compute”；
4. 可解释的打分或浅层决策树；
5. 只有前述形式明显不足时，才考虑更复杂的学习式触发器。

触发器应优先少量、稳定和可审计。不得直接使用 benchmark ID、模型名称或测试集标签记忆哪些样例应触发。

## 8. 候选动作生成

触发后不应默认评价全部动作。候选生成至少包含：

- Longest Tail 基础动作；
- 按 residual tail 排名靠前的若干替代动作；
- 与 Longest Tail 发生简单策略分歧的动作；
- 具有不同立即释放、资源脚印或 join 影响的代表动作；
- 多资源下由 Stage 4c 验证的少量极大兼容集合。

候选宽度必须有固定上限，并保留候选来源。若最优或最佳已知动作没有进入候选集合，应归因于候选召回失败；若已进入却未被选择，则归因于评价或深度不足。不能只报告最终是否改善而不区分两类问题。

## 9. Rollout 评价方式

### 9.1 深度一

对每个候选执行一个合法动作，再使用相同的固定 completion policy 推进到结束或预算边界。基础动作和 challenger 必须使用完全相同的 completion policy、tie-break 和终止条件。

### 9.2 多事件深度

深度大于一时，搜索层数按“调度决策事件”定义，而不是按任务数、时间 tick 或递归函数次数。每层只通过公共模拟器产生后继稳定状态。

需要明确区分：

- 单一路径延长：候选首动作后沿固定策略多走若干事件；
- 分支加深：每层继续比较多个动作；
- 末端 completion：达到深度后用哪个固定策略估值。

三者成本和表达能力不同，实验不得只写“depth=2”而不说明具体含义。

### 9.3 截断估值

若完整 completion 成本过高，可研究事件深度截断后的下界、剩余 tail 或稳定启发式估值。但截断值必须与完整 makespan 区分，并在小图上验证排序相关性、系统偏差和反例。不能把不可比的截断状态时间直接当作最终 makespan。

### 9.4 安全采用规则

候选只有在评价按预定协议完成，并严格优于 Longest Tail 基础动作时才采用。任何超时、状态上限、异常、候选评价不对称或无法比较，都回退 Longest Tail 并记录原因。

该规则只保证“不采纳未被评价器证明更好的候选”，不保证端到端结果不会比纯 Longest Tail 差，因为有限 completion policy 本身可能误判。必须通过 Exact 小图和真实反例测量这种误判。

## 10. 预算模型

预算至少分为：

- 每个决策的候选数量上限；
- 整图触发次数上限；
- completion 调用次数上限；
- 展开状态或节点数量上限；
- rollout 深度上限；
- 单决策墙钟上限；
- 整图墙钟上限；
- 必要时的峰值内存上限。

所有消耗都应由统一账户累计，不能让缓存命中、异常重试或 fallback 绕过统计。预算耗尽后剩余调度使用基础 Longest Tail，并保留首次及累计 fallback 原因。

正式比较包含两种口径：

1. **同搜索配置**：比较全量与选择性触发在相同宽度和深度下节省多少成本；
2. **同总预算**：让选择性方法把节省预算用于增加宽度、深度或更多关键触发，再比较最终质量。

只有第一种比较不能证明节省预算转化为更好算法，只有第二种比较也无法解释收益来自触发还是更多搜索，两者都需要。

## 11. 基线与对照组

所有正式实验至少包含：

- FIFO 或等价简单策略；
- 固定顺序策略；
- 基础 Longest Tail；
- 每个 choice state 都触发的全量 rollout；
- 固定周期触发；
- 固定概率随机触发，使用多个预先固定 seed；
- 与候选方法调用率或墙钟接近的随机/周期对照；
- 候选 selective trigger；
- 小图上的 Exact 或全首动作枚举。

多资源实验固定 Stage 4c 的 packing 规则。若同时比较不同 packing，必须采用正交实验并分别归因，不能将集合构造收益计入 selective rollout。

## 12. 数据集与实验分层

### 12.1 第一层：Stage 1--3 旧 benchmark

先使用 Stage 1--3 的单 channel、多资源随机图、回归图和攻击图开展主要算法筛选。该层用于建立决策级标签、测量触发 precision/recall、评价器误判、深度需求和等预算收益，并尽量使用 Exact 或全首动作枚举。旧 benchmark 不能单独支持真实 LLM DAG 结论。

### 12.2 第二层：100--1000 节点小图

在第一层确定触发器、候选和预算后，使用 100--1000 节点的随机图、攻击图和可追溯 real-derived slice 做完整回放，检查方法跨规模和结构来源后是否仍有净收益。

### 12.3 第三层：1--2 个中大图

只预先选择 1--2 个中大图，测量特征、触发判断、候选生成、搜索和回放的成本与超时退化。该层只做规模压力检查，不证明真实总体收益；不比较不完整 makespan。

### 12.4 开发集与冻结验证集

阈值、候选数、深度和预算只在 Stage 1--3 开发/validation 集选择。最终配置在未参与调参的 100--1000 节点验证集上冻结验证。重复结构相近的同源切片不得跨开发和验证集合造成泄漏。

## 13. 触发器评价

在具有可信标签的小图上，逐决策报告：

- 可触发 choice state 数；
- 真正值得前瞻的正例数；
- trigger precision、recall 和 F1；
- 误触发数及浪费的 completion 调用；
- 漏触发数及错失的 makespan 改善；
- 不同收益阈值下的结果；
- 按竞争形状、结构类型和决策位置分层的表现。

precision 和 recall 的正例定义必须固定。若中大图使用代理标签，应另表报告，不与 Exact 标签混合。

对端到端调度更重要的是“成本加权漏触发”：漏掉一个无影响状态和漏掉一个造成大幅 makespan 退化的状态不应等价。因此同时报告漏触发对应的可实现改善总量和最大单次损失。

## 14. 宽度与深度实验

在相同总预算下形成受控矩阵：

- 触发少量状态，每次评价更多候选；
- 触发少量状态，每个候选前瞻更深；
- 触发更多状态，但每次只比较一个 challenger；
- 宽度和深度平衡；
- 相同 completion 调用数但不同展开方式；
- 相同墙钟但不同触发器。

每个配置记录理论预算与实际消耗。若深度增加但仍使用相同次数的完整 completion，需要同时报告额外前缀展开状态和时间，不能只按 completion call 宣称成本相同。

分析应回答：

1. 改善主要来自覆盖更多错误决策，还是更准确地评价少数关键决策；
2. 深度增加到多少后收益饱和；
3. 候选宽度增加是否只是加入大量等价或低质量动作；
4. 不同规模和冲突强度下最合适的预算分配是否一致。

## 15. 消融设计

至少进行以下消融：

1. choice-only 与不触发；
2. 单一 Longest Tail 分差阈值；
3. 简单策略分歧；
4. 加入立即 compute 释放；
5. 加入 join 最后缺口；
6. 加入资源冲突或切换影响；
7. 有无 Stage 4b 结构特征；
8. 相同触发器下不同候选生成方式；
9. 相同候选下不同深度和末端 completion；
10. 有无缓存，验证结果不变并单独报告命中率；
11. 严格改善保护与无保护版本；
12. 相同调用率的随机和周期触发。

每次只改变一个主要因素。不能同时增加结构特征、候选宽度和深度后将全部收益归因于某个触发信号。

## 16. 受控反例与失败模式

至少构造或保留以下反例：

- Longest Tail 分差很小，但所有动作后续值相同；
- Longest Tail 分差很大，但基础动作仍错误；
- 立即释放大量 compute，却不影响最终关键路径；
- join 最后缺口看似关键，但另一个分支更晚到达；
- 深度一误判、深度二才能看到后续竞争变化；
- 更深搜索仍因末端 completion 偏差而误判；
- challenger 未进入候选集合；
- rollout 估值改善但端到端反而退化；
- 频繁触发导致墙钟成本远高于 makespan 收益；
- 多资源下候选集合不合法或非极大；
- 缓存 key 不完整导致不同 residual state 错误复用；
- 预算在候选之间分配不对称，造成比较偏差。

失败分析要区分触发错误、候选召回错误、评价器错误、深度不足、预算不足和实现/语义错误。

## 17. 指标与报告要求

### 17.1 调度质量

- makespan 及相对 FIFO、Longest Tail、全量 rollout 的变化；
- 小图 Exact gap、optimal rate 和首动作命中率；
- 平均、中位数、分位数和最大退化；
- 抢占次数、通信执行区间数和 forced-idle 时间；
- 多资源时的总体及逐资源利用率。

### 17.2 搜索成本

- 总 wall-clock 和算法自身时间；
- 特征计算、候选生成、前缀展开和 completion 的分项时间；
- 触发次数、触发率和未触发 choice state 数；
- completion calls、expanded states、最大深度和候选数；
- 缓存命中率、峰值内存；
- fallback 次数、原因和发生位置；
- 完整率、超时数和未完成样例。

### 17.3 净收益

同时报告质量—成本曲线，而不是只选一个配置。至少给出：单位额外墙钟带来的 makespan 改善、相同预算下的质量、相同质量下的成本，以及在没有改善样例上的额外开销。

结果依次报告 Stage 1--3 旧 benchmark、100--1000 节点验证集和 1--2 个中大图。不能排除超时或无改善样例；中大图逐例呈现，不计算总体收益。

## 18. 实验执行顺序

### 步骤一：冻结研究协议

固定 Stage 1--3 开发清单、100--1000 节点验证清单、模拟器版本、基础 Longest Tail、合法候选规则、tie-break、预算和结果格式。

### 步骤二：建立决策级标签

在小图上枚举首动作并运行 Exact，形成触发正例、负例和 unknown。记录状态来源和 benchmark hash，避免只保存脱离上下文的特征向量。

### 步骤三：评价低成本触发信号

先比较 choice-only、分差、策略分歧、立即释放和 join 条件，测量准确性与特征成本。只有简单规则证据不足时才增加复杂组合。

### 步骤四：分离候选与评价

固定触发标签，测量候选召回；再固定候选集合，比较深度、末端 completion 和预算。避免把两类问题混为一体。

### 步骤五：宽度—深度等预算实验

先在 Stage 1--3 旧 benchmark 上运行预算矩阵，再将冻结配置用于 100--1000 节点小图，同时比较全量、选择性、随机和周期触发。

### 步骤六：100--1000 节点冻结验证

冻结阈值和预算，在未参与设计的 workload/topology 上进行端到端验证，保留所有负面结果、超时和 fallback。

### 步骤七：规模与失败分析

只在预先选择的 1--2 个中大图上测量成本边界，并逐个解释完成、超时和退化。形成是否进入 Stage 4g 的受限结论。

## 19. 现有资产的使用边界

现有仓库中已有单 channel selective rollout、共享触发特征与预算对象、相关测试及实验 runner。这些资产在后续审查中可用于定位入口、复现旧结果和构造回归，但本文不假设：

- 当前特征定义就是正确或充分的；
- 当前深度参数准确表达了预期搜索树；
- 当前 completion call 统计覆盖全部实际成本；
- fallback 一定在所有异常路径上等价于 Longest Tail；
- 旧 runner 的数据集、阶段编号和结果口径仍符合当前 Stage 4 总纲；
- 旧小图收益能够推广到 72-case 真实 corpus。

下一步代码审查应以本文为检查依据，而不是反过来修改规划以适配实现。本次文档重写不包含该审查工作。

## 20. 当前证据边界

截至 2026-08-21，可以保留的谨慎背景是：旧小图上 selective rollout 曾出现受保护的局部收益，因此该方向值得继续研究；但当前真实 72-case corpus 尚无完整 holdout 收益证明。

Stage 4a 的多数竞争信息仍来自最多 8 个决策点的 sampled-prefix probe，dp>=2 和大图的完整回放成本较高。这意味着：

- 不能假设所有真实样例都有值得 rollout 的决策；
- 不能用前缀中未观察到分歧推断全图不需要 rollout；
- 不能把大图超时样例从统计中删除后宣称算法可扩展；
- 不能将合成小图或旧 complex-chain 结果外推为真实 LLM DAG 结论。

后续结果必须区分计划、假设、观察、结论和 unknown。未完成搜索不能标记为成功保护或最优。

## 21. 预期产物

本阶段应形成：

- 固定版本的 4d benchmark manifest、数据划分和实验协议；
- 小图决策级 Exact/首动作标签集；
- 触发特征定义、计算成本和版本记录；
- 触发 precision/recall、成本加权漏触发与误触发报告；
- 候选召回、评价误判和深度需求的分离分析；
- 同搜索配置与同总预算两类对照；
- 宽度—深度—触发率的质量成本曲线；
- Stage 1--3 主实验与 100--1000 节点冻结验证的端到端基线、消融和失败案例；
- 大图耗时、内存、超时和 fallback 报告；
- 说明适用范围及是否进入 Stage 4g 的结论文档。

所有结果保存输入 hash、代码版本、模拟器版本、机器环境、seed、预算、完成状态和 fallback 原因。benchmark 或公共语义变化后，不直接沿用旧标签和历史结果。

## 22. 阶段退出条件

只有同时满足以下条件，Stage 4d 才可以结束：

1. rollout 的每个分支复用公共模拟器，单 channel 与多资源动作始终合法；
2. 基础 Longest Tail、候选生成、触发器和预算账户具有独立、明确的接口与统计；
3. 小图建立了 Exact 或清楚标注边界的首动作标签，unknown 未被当作负例；
4. 触发器与 choice-only、随机、周期和全量 rollout 完成统一对照；
5. precision、recall、误触发、漏触发及其实际质量损失均已报告；
6. 候选召回失败与 rollout 评价误判已经分离；
7. 深度、宽度、触发次数和 completion 调用在同预算下完成系统比较；
8. 超时、状态上限或不完整评价始终回退 Longest Tail，并完整记录原因；
9. 在未参与调参的 100--1000 节点验证集上报告 makespan、成本、最坏退化和完整率，并对 1--2 个中大图逐例报告；
10. 特征计算和搜索开销没有被排除在算法 wall-clock 之外；
11. 对分差误导、释放误导、深度不足、缓存错误和预算不对称等失败模式有反例分析；
12. 明确说明适用的 DAG 类型、资源模型、规模、竞争强度和预算；
13. 若旧 benchmark 或 100--1000 节点验证集上没有稳定净收益，或 LLM 派生图上算法差异过小，形成“仅作分析工具”或“不进入综合算法”的结论；
14. 只有在相同预算下表现出可复现净收益的配置，才可作为 Stage 4g 的候选组件。

本阶段不以实现触发器或减少 rollout 次数为完成标志。最终必须回答：哪些决策值得搜索，收益能否从 Stage 1--3 旧 benchmark 延续到 100--1000 节点小图，以及有限中大图上是否仍可执行；若真实 LLM 派生图没有足够差异，应如实停止复杂化。
