# Stage 4a：真实 LLM Training DAG Benchmark 构建研究纲领

本阶段不是“把转换器写完”就结束，而是要建立一套能够支撑后续研究的真实 DAG 样本，并证明样本确实包含通信竞争。主要输入来自 `third_party/simai-flow-scheduler` 的 AICB workload 和 topology。

## 1. 研究问题

要回答三个问题：

1. AICB workload 和 topology 能否在不改变训练依赖的前提下转换成项目的固定资源 DAG；
2. 原始 workload 是否产生足够的通信竞争，哪些参数会增强或削弱竞争；
3. 在实验耗时可接受的条件下，应该保留哪些规模、模型、DP 和 job 组合。

没有竞争的 DAG 不是失败，但只能作为负面对照，不能作为调度算法效果的主要证据。

## 2. 输入与转换假设

盘点 `inputs/aicb-workload`、`inputs/topologies` 以及 SimAI 的解析和任务展开逻辑，记录每个输入的模型、world size、TP、PP、DP、micro-batch、iteration 和 topology。转换时：

- 保留原始任务的计算/通信类型和依赖；
- 将通信映射为固定且非空的资源集合；
- 固定 route 和带宽换算方式，避免运行时动态选路；
- 为不同 job 添加命名空间，但不把不同 job 的任务错误连接；
- 输出自包含 JSON，并保存来源 hash、转换参数和资源映射。

需要用手工极小图逐项核对：依赖释放、计算连续运行、通信暂停/恢复、资源原子获取和最终完成状态。手工图只用于验证转换语义，不用于替代真实结构研究。

## 3. 竞争构造实验

### 3.1 增加 DP

从同一个 workload 出发，逐步增加 DP 数量，观察跨 DP 通信是否落到相同资源集合。每个 DP 配置都记录：同时合法通信数、资源相交边数、竞争持续时间、可选事件数、FIFO 与 Longest Tail 是否作出不同选择。若只增加任务数而没有增加资源冲突，应明确记为无效扩展。

### 3.2 增加 job

两种方式分别实验：

- 重复同一个 AICB workload，给每个副本独立 job 标识；
- 选择不同模型或并行配置的 workload，转换后混合到同一集群。

job 之间只共享资源，不共享训练依赖。分别比较 1、2、3、4 个 job，并记录竞争密度和每个 job 的完成时间。不同 workload 混合时保留每个 job 的来源，不能只保存合并后的图。

### 3.3 规模控制

普通样例覆盖小、中、大三个等级。超大 DAG 控制在约 10 个，用于观察运行时间、内存和算法退化；不要求对它们求 Exact。生成、转换、竞争扫描和每个算法都设定时间预算，超时必须保留状态并报告。

## 4. 竞争准入标准

正式竞争样例至少满足以下条件中的两项：

- 存在两个或更多同时合法的通信；
- 至少一对候选通信资源集合相交；
- 至少出现一次通信暂停/恢复会改变后续 ready 集合；
- FIFO、Longest Tail 或一个简单替代策略在首个选择点给出不同动作。

准入报告还要包含无竞争样例数量，避免只挑选有利数据。按 workload、topology、DP、job 数量和规模分层保存清单。

## 5. 基线与实验

每个样例至少运行 FIFO、基础 Longest Tail 和一个固定顺序的简单策略。小图额外运行 Exact，核对最优 makespan、最优首动作和 trace 合法性。大图只比较完成时间、运行时间、抢占次数、forced-idle、资源利用率和未完成状态。

## 6. 研究产物

- 输入资产清单和可复现转换命令；
- DAG schema、来源和内容 hash；
- DP/job 扩展实验表；
- 竞争扫描和准入报告；
- 按规模分层的 benchmark manifest；
- 约 10 个超大 DAG 的耗时报告；
- 无竞争、转换失败和超时样例的单独清单。

## 7. 退出条件

只有同时满足以下条件才结束 4a：

1. 真实输入转换的依赖、资源和 trace 语义经过小图和端到端检查；
2. 正式 benchmark 中每个样例都有可解释的竞争报告；
3. DP 增加和 job 混合对竞争强度的影响有实验曲线，而不是口头判断；
4. 普通规模和约 10 个超大规模样例的运行时间预算已经测量；
5. 形成“哪些输入无竞争、哪些输入适合后续算法研究”的明确结论。
