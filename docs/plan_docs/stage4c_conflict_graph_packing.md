# Stage 4c：固定多资源冲突图与兼容集合选择规划

## 1. 阶段定位

本阶段研究固定多资源 DAG 在一个调度事件上应当同时推进哪些 communication。它承接 Stage 3 的多资源公共语义，先以 Stage 3 旧 benchmark 为主要实验输入，再用 100--1000 节点小图验证，Stage 4a 真实 benchmark 只保留少量代表性样例用于迁移与规模检查。

本阶段的核心不是为已有 packing 代码补充说明，而是独立回答三个问题：

1. 如何稳定、低成本地构造合法且 work-conserving 的通信集合；
2. 当存在多个合法极大集合时，怎样比较它们对剩余 DAG 的长期影响；
3. 比 Longest Tail 顺序贪心更复杂的集合构造，是否先在旧 benchmark 上形成稳定收益，并能迁移到较小的 LLM 派生图。

现有构造器、特征、实验脚本和历史结果只作为待审查资产。它们可以提供实现入口、受控反例和复现实验，但不能定义问题，也不能证明某种方法已经有效。

## 2. 本阶段不处理的内容

为避免把不同问题混在一起，本阶段不处理：

- 动态路由、路径迁移、部分获取资源或按比例共享带宽；
- 主动 `WAIT`，或故意返回非极大集合来保留资源；
- 改变 compute 自动开始、不可抢占和可并行的公共语义；
- 用算法自行推进时间、释放依赖或修改通信剩余工作；
- 把 barrier 设计成独立全局优先级，其增量作用留给 Stage 4e；
- 把 rollout 触发与预算分配作为主要问题，其系统研究留给 Stage 4d；
- 把 job 公平性或 JCT 混入单 job makespan，多 job 目标留给 Stage 4f；
- 在完整真实图上声称最优，或用实验最优率替代理论保证。

若使用浅层前瞻，只能把它作为集合候选质量的受控诊断工具，并单独报告额外预算，不能将其收益归因于纯 packing。

## 3. 问题定义与动作契约

设固定通信资源集合为 $\mathcal R$。每个 communication $i$ 在输入中预先绑定非空资源集合 $R_i\subseteq\mathcal R$。通信启动或恢复时必须同时取得全部所需资源，暂停或完成时一次性释放；恢复后资源集合不变。

在离散事件点，公共模拟器完成同一时刻的所有任务事件和零时长闭包，自动启动 ready compute，然后给出 eligible communication 集合 $E(s)$。算法返回动作 $A\subseteq E(s)$，且必须满足：

1. **非空**：存在 eligible communication 时，动作中至少有一个通信；
2. **资格合法**：$A$ 中所有通信都属于 $E(s)$；
3. **资源兼容**：任意不同的 $i,j\in A$ 满足 $R_i\cap R_j=\varnothing$；
4. **极大性**：不存在 $k\in E(s)\setminus A$，使 $A\cup\{k\}$ 仍资源兼容；
5. **确定性**：固定输入、状态、参数和 tie-break 时返回相同动作。

第 4 条要求的是 inclusion-maximal，即“不能再直接加入一个通信”，不是 maximum cardinality，也不是最大权重集合。通信数量最多、占用资源最多或分数总和最大都不是目标语义。算法可以在多个极大集合中选择，但不能通过返回非极大集合主动闲置仍可利用的资源。

模拟器负责验证动作并执行状态转移。算法只能读取只读的当前剩余状态，不得读取答案提示、reference result 或用于分类的 metadata。

## 4. 冲突图表示及其边界

对当前状态 $s$ 构造冲突图 $G_s=(V_s,F_s)$：

- 顶点 $V_s=E(s)$；
- 若 $R_i\cap R_j\neq\varnothing$，则 $(i,j)\in F_s$；
- 合法兼容集合对应独立集；
- work-conserving 动作对应极大独立集。

冲突图只表示当前哪些通信不能并行，不包含以下决定长期价值的信息：

- communication 的剩余工作量；
- 完成后立即释放的 compute、join 或下一层 communication；
- 下游剩余关键路径和未来资源需求；
- 尚未 eligible 但即将由 compute 完成释放的通信；
- 不同顶点共享的下游节点及由此造成的重复计分。

因此，同构冲突图不必有相同的最佳动作，静态最大独立集也不是本问题的充分解法。冲突图用于构造当前合法动作；集合价值必须结合 residual DAG 判断。

## 5. 研究问题与待验证假设

### 5.1 基础问题

本阶段首先回答：

1. 真实 benchmark 中有多少决策点存在两个以上不同极大兼容集合；
2. Longest Tail 顺序补全在哪些冲突形状和 DAG 结构上会选择较差集合；
3. 失败主要来自顶点排序不准，还是逐点贪心无法表达集合互补；
4. 多起点、局部交换或整集合评分能否修复这些失败；
5. 修复是否在未参与设计的真实 workload/topology 上稳定，并且成本可接受。

### 5.2 候选假设

以下内容只作为待验证假设，不预写为结论：

- 单个占用多资源的高 tail 通信，可能不如多个分别占用这些资源的通信组合；
- 多个单点分数一般的通信，可能共同释放不同关键分支；
- 逐点累加下游分数可能因共享后继而重复计分，按集合取并集可能更可靠；
- 热点资源负载可以帮助打破 tail 接近时的平局，也可能把局部拥塞误当作最终瓶颈；
- 多起点和有限交换可能覆盖多数真实贪心失败，无需枚举大量极大集合；
- 若真实冲突图通常是团、空图或只有唯一极大集合，复杂 packing 的价值可能很低。

每条假设都必须给出适用条件、真实样例频率和反例。

## 6. 输入范围与准入条件

实验不再把 Stage 4a 的完整真实 DAG 作为主要输入。第一轮先使用 Stage 3 固定多资源 benchmark 完成算法筛选、Exact 对照、反例和消融；第二轮使用 100--1000 节点、资源映射明确且 trace 可回放的小图检查迁移效果；最后只选择 1--2 个中大图进行规模与成本检查。来自 Stage 4a 的样例仍需保留内容 hash、转换版本和竞争审计等级。

样例按决策证据分层：

- **集合唯一**：完整回放或有界认证范围内，每个观察到的决策点只有一个极大集合；用于语义回归，不用于证明复杂算法有效；
- **集合可选**：至少一个决策点认证或观察到多个极大集合；是主要质量比较对象；
- **策略分歧**：简单构造器实际返回不同集合；用于分析选择机制；
- **收益敏感**：不同首动作或策略造成 makespan 差异；小图优先用 Exact 认证，大图只能记录观察；
- **未知**：因 sampled prefix、超时或候选枚举受限，不能判断全图是否存在集合选择。

最多 8 个决策点的 prefix probe 只能支持前缀观察，不能把没有观察到多集合写成全图无选择。dp>=2 和大图若无法完整回放，应保持 unknown，并通过真实切片或事件窗口做局部研究。

## 7. 数据集分层

### 7.1 第一层：Stage 3 旧 benchmark

以 Stage 3 固定多资源随机图、回归图、攻击图和手工资源脚印图为主要开发与筛选集合。小图应尽可能枚举当前状态的全部极大集合，并用 Exact 给出最优 makespan 或最优首动作集合。这一层用于判断 packing 机制是否成立，不用于声称真实 LLM DAG 收益。

### 7.2 第二层：100--1000 节点小图

在第一层筛选后，使用 100--1000 节点的随机图、攻击图和可追溯 real-derived slice 做完整端到端验证。要求 FIFO packing、Longest Tail packing 和候选算法在统一预算内完成，并具备独立 trace 验证。

### 7.3 第三层：1--2 个中大图

只预先选择 1--2 个中大图，用于测量冲突图构建、特征计算、候选构造、模拟回放、内存和超时退化，不承担真实总体收益证明。若完整回放不可行，不比较不完整 makespan。

## 8. 基线与算法层次

所有方法都必须产生合法极大集合。研究从最简单方法逐层增加能力，每层只改变一个主要因素。

### 8.1 简单基线

1. **固定顺序补全**：按稳定 task ID 或规范化顺序依次加入兼容通信，用于发现输入顺序依赖；
2. **FIFO 补全**：按 eligible/ready 时间和稳定 tie-break 排序后贪心补全；
3. **Longest Tail 补全**：按当前 residual tail 排序后贪心补全，是主要质量基线；
4. **随机顺序补全**：固定 seed，用于判断复杂方法是否只获得偶然集合多样性；
5. **小图全部极大集合**：只作 Oracle 候选空间或诊断，不作为大图算法。

“补全”必须一直进行到集合极大。不同顶点评分不得悄悄使用不同补全规则，否则无法区分顶点优先级与集合构造的收益。

### 8.2 候选集合构造

按复杂度依次研究：

1. **单次顺序贪心**：确定性地得到基线集合；
2. **多起点贪心**：强制若干不同通信成为起点，再用相同顺序补成极大集合；
3. **有限局部交换**：从基线移除一个成员，加入一个或少量冲突候选，再补成极大集合；
4. **有界极大集合枚举**：仅在 eligible 数量和预算允许时生成部分或全部极大集合；
5. **受控集合前瞻**：只用于比较候选集合的长期影响，严格限制候选数、模拟调用数和墙钟预算。

每个构造器始终保留确定性 Longest Tail 贪心作为安全 fallback。预算耗尽、无替代集合或时间限制必须记录原因，不能静默返回基线后仍标记为高级方法完成。

### 8.3 集合评分

集合评分与候选构造分开审查。候选特征包括：

- 集合内 residual tail 的最大值、分布或受控聚合；
- 完成本次通信后可能立即释放的 compute 工作；
- 下游未完成节点并集，而不是逐顶点下游简单相加；
- 下游固定资源需求和热点资源压力；
- 集合资源互补程度、资源覆盖和多资源通信代价；
- Stage 4b 已验证的训练角色或重复结构特征。

所有分数必须基于当前剩余状态。原始 duration、静态关键路径或完整 DAG 总量若不能随完成和抢占更新，不得冒充 residual 特征。LLM role 等字段必须来源稳定，并与不使用 role 的版本消融。

## 9. 候选预算与降级规则

每个决策点明确限制：参与精细评分的通信数、多起点数量、构造操作次数、保留的极大集合数、完整补全模拟调用数、单决策与整图墙钟预算，以及适用的内存或状态上限。

达到预算时返回已经验证合法的基线集合，并记录预算类型、已生成和已评价集合数、构造耗时及是否降级。若候选算法和基线使用不同总墙钟，应同时提供等预算比较；不能用无限制搜索对比低成本 Longest Tail 后只报告 makespan。

预算参数只在开发或 validation 集选择，之后固定用于 100--1000 节点验证集，不得为每个测试图单独调参。

## 10. 正确性审查

### 10.1 动作级检查

对每个构造器验证：

- 返回非空、无重复、稳定排序的 eligible communication；
- 集合内资源两两不相交，且满足 inclusion-maximal；
- 输入状态不被修改，相同状态和参数结果确定；
- 空预算和中途超时时仍返回合法基线；
- 单 channel 退化情形恰好选择一个通信。

### 10.2 状态与 trace 检查

所有策略复用公共模拟器。独立 trace validator 至少检查依赖、通信工作量守恒、compute 连续性、固定资源排他、同一时刻事件闭包、forced idle 和最终完成状态。集合构造器不得直接实现另一套时间推进。

### 10.3 枚举与 Exact 对拍

在小图上将构造器结果与全部极大集合核对，检查有界枚举是否如实报告未覆盖部分，比较压缩与未压缩 Exact，并记录每个极大首动作的最优后续值。要区分“最优首动作之一”“最终达到最优”和“仅在某个补全策略下更好”。

一步 Longest Tail 补全得到的估值不是 Exact 标签。使用同一 heuristic 完成的前瞻，只能称为该完成策略下的 rollout 估值。

## 11. 受控反例设计

至少覆盖以下机制，每个 motif 只设置一个主要目标：

- **团冲突**：所有通信两两冲突，验证退化为单通信选择；
- **空冲突图**：所有通信兼容，唯一极大动作包含全部通信；
- **宽通信对多个窄通信**：一个多资源通信与多个彼此兼容通信竞争；
- **路径或星形冲突**：最大数量、最高单点分数和最佳长期集合不同；
- **局部交换修复**：顺序贪心失败，但一次有限交换可修复；
- **相同冲突图、不同下游 DAG**：证明冲突图不足以决定选择；
- **共享下游**：暴露逐通信分数相加的重复计分；
- **热点误导**：资源负载高但不在最终关键路径；
- **抢占诱导退化**：频繁改变集合却不降低 makespan；
- **极大但非最大数量**：验证 work-conserving 不等于通信数量最多。

这些图用于定位机制和回归，不与真实 benchmark 混合统计总体收益。

## 12. 真实图结构统计

在运行复杂算法前，先统计每个可完成样例和决策点的：

- eligible communication 数，冲突边数、密度、连通分量和最大度；
- 资源数量、资源脚印大小、多资源通信比例；
- 各资源候选数和剩余通信负载；
- 极大集合数量或有界下限、集合大小分布及是否唯一；
- FIFO、Longest Tail、固定顺序是否产生不同集合；
- 训练角色、pipeline 阶段和 job 归属组成，但只作为分层变量；
- 多集合决策在完整执行中的次数和时间位置。

完整枚举不可行时，必须标明统计是精确值、下界、sampled prefix 还是预算内观察值。不能把“只找到一个集合”写成“只有一个集合”。

## 13. 实验设计

### 13.1 动作契约与候选覆盖

在手工小图和随机小冲突图上比较构造器的合法率、确定性、候选去重、极大集合覆盖率和预算降级行为。此实验先证明构造基础可靠，不评价 makespan 收益。

### 13.2 小图质量

在 Stage 3 小图、攻击图和 real-derived slice 上，以 Exact 或全首动作值为参照，报告首动作最优命中率、最终 optimal rate、平均/分位数/最大 gap、候选是否包含最优首动作，以及构造和评价的独立耗时。

通过“候选覆盖上限”分离生成问题和评分问题：最优动作不在候选中时，问题在构造；候选已有最优动作却未选中时，问题在评分或前瞻。

### 13.3 100--1000 节点端到端对照

在第一层通过筛选的配置上，使用 100--1000 节点小图运行固定顺序、FIFO、Longest Tail 贪心、多起点、有限交换和必要的集合评分。固定模拟器、输入 hash、tie-break、seed、机器环境和预算。

比较 makespan 相对 FIFO 与 Longest Tail 的变化，并报告逐样例最坏退化。按 topology、模型族、规模、冲突密度、多资源比例和策略分歧次数分层，避免大量无选择决策稀释结果。

### 13.4 成本与规模

在预先选择的 1--2 个中大图上测量冲突图构建、residual 特征、候选构造、集合评分和模拟回放时间，并报告内存。该实验只检查规模边界，不用少量样例推断普遍算法收益。

### 13.5 泛化与反例

阈值和预算在 Stage 3 开发集固定后，在未参与调参的 100--1000 节点验证子集上检查。对明显退化样例逐个分析当前状态、冲突图、候选与所选集合、后续释放、抢占变化和最终 makespan 差异。

## 14. 消融要求

至少进行以下消融：

1. 相同 Longest Tail 分数下，单起点与多起点；
2. 相同候选集合下，顶点聚合与下游并集评分；
3. 有无有限局部交换；
4. 有无资源热点特征；
5. 静态量与正确 residual 量对照，用于暴露状态更新错误；
6. 有无 LLM role/结构特征；
7. 相同候选数下，直接评分与浅层完成模拟；
8. 相同墙钟下，更宽候选与更深评价；
9. 安全 fallback 与预算充足正常路径。

每次只改变一个因素。若同时改变构造、评分、候选数量和预算，结果不能归因于某个 packing 机制。

## 15. 指标与报告格式

每个算法至少报告：

- makespan 及相对 FIFO、Longest Tail 的变化；
- 小图 Exact gap、optimal rate、首动作命中率和候选覆盖率；
- 完整率、超时数、fallback 次数与原因；
- 总 wall-clock、每决策构造时间、评分时间和模拟时间；
- 候选数、评价数、交换次数和构造操作数；
- 决策数、实际策略分歧数、集合大小分布；
- 抢占次数、通信执行区间数、forced-idle 时间；
- 总体及逐资源利用率；
- 峰值内存或适用的内存指标。

结果依次汇总 Stage 3 旧 benchmark、100--1000 节点验证集和 1--2 个中大图。前两层报告统计量和逐样例表；中大图逐例报告，不计算缺乏意义的总体均值。

## 16. 现有资产的审查顺序

建议按以下顺序核对，但不以现有接口约束规划：

1. 公共多资源模拟器和动作验证，确认 eligible、兼容性、极大性及事件推进；
2. `src/muti_channel/preemptive/packing.py`，核对冲突图、预算、合法动作验证和统计；
3. `src/muti_channel/preemptive/constructors.py`，核对贪心、多起点、交换和有界枚举；
4. `src/muti_channel/preemptive/solver.py`，确认 residual 分数、候选选择、fallback 和模拟器复用；
5. `src/llm_structured/packing_features.py`，核对特征是否来自当前状态且定义稳定；
6. `benchmark_generate/llm/packing_motifs.py`，检查 motif 是否只隔离一个机制；
7. `experiments/llm_structure/packing_evaluation.py` 及 Stage 3 runner，检查阶段编号、输入、预算、超时和结果口径；
8. 对应 tests，检查是否覆盖独立语义和失败模式，而不只是代码自洽。

当前文件或函数名可能保留旧阶段编号，不能据此判断研究已完成。若实现与公共语义不一致，先用最小图确认，再修改最小必要模块并补回归测试。

## 17. 实施步骤

1. **冻结研究协议**：明确 manifest、模拟器版本、数据分层、holdout、预算和 tie-break，建立“顶点评分—构造器—集合评分—fallback”配置表。
2. **审查公共语义**：用团、空图、宽对窄和零时长释放样例检查动作与事件边界，非法集合由模拟器拒绝而非静默修正。
3. **建立小图真值**：枚举全部极大动作，与 Exact 和未压缩状态交叉验证，保存输入 hash、最优值、最优首动作和求解状态。
4. **先运行 Stage 3 主实验**：逐层评价构造器，淘汰没有稳定增量价值的方法。
5. **再运行 100--1000 节点验证**：冻结配置后检查跨规模和 real-derived 结构迁移。
6. **最后检查 1--2 个中大图**：只测完成能力、时间、内存和 fallback。
7. **形成受限结论**：若 LLM 派生图中算法差异仍小，明确记录 Longest Tail 已足够或复杂 packing 不值得。

## 18. 预期产物

本阶段应产生：

- 固定版本的 4c 实验 manifest 与运行配置；
- 真实图冲突结构和极大集合多样性 census；
- 动作契约、预算降级和 trace 回归测试；
- 一组目标单一、可由 Exact 或手工验证的攻击样例；
- 小图 Exact/首动作对照结果；
- Stage 3 旧 benchmark 的统一基线、候选算法和消融结果；
- 100--1000 节点小图验证结果；
- 1--2 个中大图的成本、内存、超时和 fallback 报告；
- 失败案例、适用范围及记录审查发现的 process 文档。

结果文件记录输入 hash、代码版本、环境、预算、算法配置和完成状态。benchmark 或模拟语义变化后，不直接沿用旧 reference result 或历史表格。

## 20. 阶段退出条件

只有同时满足以下条件，Stage 4c 才可以结束：

1. 固定多资源动作契约与公共模拟器一致，所有算法只选择合法极大集合；
2. 构造器通过合法性、确定性、只读状态和预算降级测试；
3. 小图极大集合枚举与模拟器、Exact 完成交叉验证，未完成 Exact 如实标记；
4. 已按“Stage 3 旧 benchmark—100--1000 节点小图—1--2 个中大图”的顺序完成分层实验；
5. 完成固定顺序、FIFO、Longest Tail 贪心和候选 packing 的统一对照；
6. 候选生成与候选评分的贡献通过覆盖率和消融分离；
7. 在冻结的 100--1000 节点验证集上完成收益与退化报告，中大图逐例报告且不外推总体收益；
8. 运行时间、内存、候选数、抢占、forced idle 和资源利用率与 makespan 一同报告；
9. 宽通信阻塞窄通信、共享下游重复计分、热点误导和频繁抢占等失败模式有反例分析；
10. 明确算法适用的 workload、topology、资源规模、冲突形状和预算；
11. 若复杂构造没有稳定净收益，形成“Longest Tail 贪心已足够”或“仅限某类图”的否定/受限结论；
12. 只有通过上述验证且成本值得的组件，才允许进入 Stage 4g。

本阶段不以实现了若干构造器或在少量 motif 上优于基线为完成标志。最终需要回答的是：复杂 packing 在 Stage 3 benchmark 上是否稳定有效，能否迁移到 100--1000 节点小图，以及当前 LLM 派生图缺少明显算法差异时，相对 Longest Tail 贪心多付出的成本是否值得。
