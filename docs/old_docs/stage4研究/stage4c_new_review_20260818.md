# Stage 4c 固定多资源冲突图打包审查

## 1. 审查范围与编号说明

本审查依据 `outline.md`、`stage4_LLM_search.md` 和 `stage4c_conflict_graph_packing.md`，检查当前固定多资源、可抢占通信场景的冲突图打包实现。正式编号中的 Stage 4c 是“固定多资源冲突图打包”；历史过程文档和结果中写作 `stage4f_packing` 的内容，实际对应本阶段。这样处理是为了避免把历史编号当成当前计划的阶段。

本阶段的目标不是重新实现模拟器，而是让算法在同一个合法状态转移上构造资源兼容的通信集合，并评估“先选哪一组通信”对 makespan 的影响。通信必须同时取得所需资源，集合应当资源不冲突、不可再加入其他合法通信，调度必须保持工作守恒；算法不得自行推进时间或使用参考答案。

## 2. 已检查的实现

主要实现包括 `src/muti_channel/preemptive/packing.py`、`constructors.py`、`solver.py`，结构特征在 `src/llm_structured/packing_features.py`，实验入口为 `experiments/llm_structure/packing_evaluation.py`，固定样例由 `benchmark_generate/llm/packing_motifs.py` 生成。测试覆盖打包契约和特征基本性质。

当前代码能从 eligible communication 集合建立资源占用图，生成非空且包含极大合法动作的候选集合，并交给公共多资源模拟器执行。最长剩余路径的贪心选择是确定性的；候选构造器保持只读，不修改模拟器状态；最终轨迹能通过公共 trace validator 检查。

## 3. 结果与可复现证据

已登记的六个打包 motif 均能得到合法轨迹，Exact 与轨迹校验均通过。两个 motif 中最长尾贪心结果为 16，而 Exact 为 14；加入多种随机种子并配合深度一的后续评估时可以达到 14。这说明“只按单个通信排序”确有改进空间，也说明小图上的验证链路基本可用。

但历史结果文件中的 `real` 数组为空，因此不能把这六个 motif 当成真实 LLM 负载证据。历史决策引用的 40 个多资源案例只是有界抽查，其中仅 3 个案例、7 个观察到的选择状态，不足以估计成功率、平均差距或泛化能力。结果中的“constructor comparison”也不能按字面解释为构造器质量比较，见下节。

## 4. 必须修正的问题

### 4.1 非 rollout 构造器没有真正被执行

`multi_seed`、`one_exchange`、`enumerate_bounded` 返回的 `PackingResult.selected` 都是 baseline。`schedule_bounded_packing(..., rollout=False)` 又始终执行 `packed.selected`。因此 `lt_multi_seed`、`lt_exchange`、`lt_enumeration` 在不启用 rollout 时保证执行同一条贪心基线，现有比较不能说明三个构造器谁更好。应让结果明确携带候选集合，或者在调度器中按算法选择真正的 selected，并增加一个能区分候选动作的回归样例。

### 4.2 `max_sets` 没有限制枚举成本

`enumerate_bounded` 先调用 `model.maximal_actions(state)` 完整枚举，再切片。大 eligible 集合可能在切片前就消耗大量时间和内存，`max_sets` 不能承担预算保护作用。应使用带上限的回溯枚举，并在达到上限时记录截断状态；若无法安全提前停止，应把实际枚举量纳入独立预算。

### 4.3 评估预算可能被超出

外层只在 `calls < budget.b_eval` 时调用候选评估，而 `choose_by_depth1_longest_tail` 可能为每个候选执行一次完整模拟。因此一次调用可消耗多个 completion call，最终超过 `b_eval`。预算应在每次候选完成前预留，或把候选模拟改成可中止的共享预算接口，并在结果中报告 `budget_exhausted`。

### 4.4 统计字段不能反映真实运行

`planner_triggered` 目前是 `int(calls > 0)`，表示整条 schedule 是否触发过，而不是触发次数。构造器的回退原因、实际候选数、运行时间和操作数也没有完整传到最终结果。没有这些字段，无法判断收益来自何种动作，也无法比较开销。

### 4.5 边界约束含义不清

`PackingBudget` 允许所有字段为零。尤其 `max_sets=0` 时 baseline 仍被保留，调用者无法区分“禁止枚举”和“至少保留基线”。应定义零值语义、非法负值处理和 fallback 原因，并在 JSON 结果中保存配置快照。

## 5. 测试和证据缺口

现有测试主要验证动作合法性和特征读取，仅有一个较小的特征测试；没有 score 与 constructor 正交比较、最优动作集合召回率、候选截断、预算严格上限、真实留出集以及随机/攻击集分层。需要用手工构造的两个候选动作不同且最优动作已知的小图，先证明调度器确实执行了非 baseline 候选。

代码质量检查还发现相关模块存在未使用导入、导入顺序、默认可变对象构造等问题；这些不是当前语义错误，但会妨碍维护。完整测试当前为 169 passed，不能据此推断打包比较有效。

## 6. 分阶段判断

| 检查项 | 判断 |

| 固定资源和集合合法性 | 已基本满足，可继续复用 |
| 与公共模拟器、轨迹验证衔接 | 已满足小图要求 |

## 7. 审查结论

Stage 4c 已完成“合法打包动作和最小验证骨架”，尚未完成“可解释、受预算约束且经独立数据验证的打包算法”。应保留确定性的最长尾基线和六个 motif 作为回归材料，但暂停把历史 constructor 或 multi-seed 结果作为算法结论。先修正候选传递、枚举上限、评估预算和统计字段，再进行分层 benchmark 与真实 holdout；在此之前，本阶段只能标记为开发中。

## 8. 逐项核对清单

状态转移方面，应逐事件确认所有 compute 在 ready 后自动连续完成，通信暂停只保留剩余工作；动作选择不得改变依赖释放顺序。资源方面，应记录每个通信的完整资源集合，启动和恢复必须一次性获取全部资源，完成或暂停时一次性释放。集合方面，空集合只能在没有 eligible 通信时出现；存在可运行通信时不得借打包名义主动空闲。

数据方面，每个 benchmark 必须自包含，metadata 不得暗示答案；reference result 只供评估读取。每次结果应保存输入 hash 和语义版本，避免修正后沿用旧最优值。复现方面，固定种子、Python 版本、预算和算法配置必须写入结果；超时、状态上限和 fallback 要和正常完成分开统计。

## 9. 风险排序

最高风险是候选没有真正传到执行器，这会使所有质量结论失效；其次是无限枚举和超预算评估，可能在大图上失去可用性；再次是统计字段过少，导致无法解释退化。未使用导入等风格问题排在其后，可在契约修正后集中清理。真实数据缺失不是代码 bug，但在进入研究结论前必须补齐。

## 10. 按文件审查记录

`packing.py` 应只负责候选动作的数据结构、合法性和评分所需的只读信息。当前 baseline 与 selected 含义混在一起，调用者看不到“构造到了什么”和“最后执行了什么”的区别。建议把构造结果与决策结果拆开，避免字段名称继续掩盖问题。

`constructors.py` 的贪心构造满足确定性和包含极大要求，可以保留为最小基线。多种种子、一次交换和有界枚举的共同问题是候选集合虽被计算，却没有稳定的选择契约；其中枚举还缺少生成过程上限。这里不应调用模拟器推进时间，只能读取 eligible、剩余工作和固定资源集合。

`solver.py` 是问题最集中的边界。它既选择构造器，又决定是否做后续评估，还负责把动作交给模拟器。现有 `calls` 在多个层级分别理解，导致预算看似存在但无法严格兑现。需要一个单一记账对象，并保证异常、回退和正常完成都更新相同字段。

`packing_features.py` 的资源 footprint 和冲突图可用于解释，但特征必须从当前剩余状态计算。若通信已经部分完成，原始 duration 不得继续充当剩余工作。对资源互补的解释也必须基于尚可加入的 eligible 通信，而不是整个 DAG。

`packing_evaluation.py` 当前能跑通六个 motif，却没有建立训练、开发、留出边界。输出应保留每个构造器实际执行的动作序列；否则即使 makespan 相同，也无法知道是候选相同还是不同候选碰巧同结果。

## 11. 最小复现实例建议

建立三个小图。第一个图包含三个通信，其中两个资源不冲突，验证动作必须包含二者而不能只选一个。第二个图让最长尾基线先占用关键资源得到 16，交换候选得到 14，验证 non-rollout 也能执行交换结果。第三个图制造大量极大集合但把 `max_sets` 设为 2，验证构造过程本身只产生两个结果且记录截断。

对每个图保存决策时刻、eligible 集合、候选动作、资源占用、实际 selected、下一事件和最终 makespan。这样可以手工核对候选传递、资源合法性和预算计数，避免只依赖端到端数字。

## 12. 不能从现有结果推出的结论

六个 motif 全部 Exact 最优不能说明算法在随机或真实图上最优；两个 motif 的 16 到 14 不能说明 multi-seed 一般有效，因为改进依赖 rollout 且样本由开发过程反复查看；40 例 census 也不能说明冲突选择罕见，因为多数案例可能在限定时间前没有走到关键状态。任何论文或阶段总结都应把这些限定条件写在数字旁边。
