# Stage 4c 修正与继续推进方案

## 1. 目标和完成标准

本方案针对正式 Stage 4c。历史文件名中的 `stage4f_packing` 均视为本阶段旧记录。完成标准是：每一个返回的候选动作都能被调度器实际执行；所有枚举和完成评估严格受预算限制；轨迹、资源和剩余工作仍由公共模拟器负责；结果能区分最优、可行但超时、回退和预算耗尽；在随机、攻击和真实留出集上分别报告收益与开销。

## 2. P0 正确性修正

第一步修改 `PackingResult` 的数据契约，使其同时保存 baseline、候选集合、最终选择、构造器名称、候选数量、是否截断和回退原因。`schedule_bounded_packing` 必须执行 result.selected，而不是无条件执行 baseline。加入一个两候选动作 makespan 不同的固定小图，断言 multi-seed、exchange、enumeration 在关闭 rollout 时能产生不同于 baseline 的结果。

第二步重写有界枚举。回溯过程每加入一个合法资源集合就立即产生极大化结果；达到 `max_sets` 后停止继续扩展，并返回 `truncated=true`。禁止先调用无限制 `maximal_actions` 再切片。对于 `max_sets=0`，明确规定为“禁用额外候选、只保留 baseline”，并在结果中写入该语义；负值直接报参数错误。

第三步建立统一的 completion-call 记账器。每次候选模拟前检查剩余次数和剩余时间，模拟器在完成一个事件后也检查限制；无法中断的调用必须预留完整额度，不能事后才发现超出。结果至少包含 `eval_calls`、`eval_time_ms`、`budget_exhausted`、`timeout` 和 `status`。

第四步将 `planner_triggered` 改为整数计数，并另存 `planner_decisions`。构造器操作数、候选被选次数和 fallback 原因应在每次调度及最终汇总中保持一致。不要把一次触发压缩为布尔值。

## 3. P1 测试与接口同步

补充以下回归测试：资源冲突不能同时启动；互不冲突资源必须尽量并行；暂停后剩余工作守恒；候选被执行后 trace 与公共 validator 一致；枚举达到上限时不再增长；评估次数永不超过预算；超时和 Exact 未完成均不能标为最优；零预算行为稳定；随机种子相同结果可复现。

同步 schema、loader 和 CLI 输出，禁止算法读取 metadata 或 reference result。结果 JSON 增加 benchmark hash、语义版本、预算、状态和统计字段。对每个历史 result 重新生成 hash；如果语义或候选选择变化，旧表格只能保留为历史，不得覆盖。

## 4. P2 受控实验

先运行三组正交实验：固定 scoring、比较四种 constructor；固定 constructor、比较最长尾、资源互补和一步完成评估；固定算法、分别改变 `max_sets`、completion 次数和时间预算。每组都包含随机、攻击和 motif 三类，并报告 makespan、最优率、平均/最大差距、触发次数、候选数、抢占次数、强制空闲时间、资源利用率和运行时间。

最优动作集合召回率应在小图上以 Exact 的全部并列最优首动作作为集合，而非只比较一个动作。对 16 对 14 的两个 motif 给出完整 trace 和每次选择，说明改进来自哪一个候选。任何“多种种子达到最优”的结论都必须同时报告额外评估成本。

## 5. P3 真实留出集

从 Stage 4a 已冻结的真实 R-P、R-S 数据中提取固定资源投影；训练或阈值选择只使用开发集，真实留出集只用于最终一次报告。若真实数据尚未包含多资源通信，应在生成器中增加明确资源占用和拓扑来源字段，保留输入 hash 和转换版本。不得用历史空的 `real` 数组替代真实证据。

## 6. 继续或停止条件

修正后，若非 baseline 构造器在小图上能实际改变选择，且所有预算严格满足，则进入 P2。若在独立留出集上平均差距不劣于最长尾、最坏情况不出现不可解释退化，并且额外开销有上限，才考虑注册为候选算法。若收益只存在开发 motif、或评估开销无界，则保留为分析工具，不进入公开算法。

## 7. 预期交付物

交付修正后的打包契约、四类回归测试、重新生成的 reference/实验 JSON、随机/攻击/真实三类汇总表，以及一份注明历史编号迁移的结果说明。所有未完成 Exact 或预算耗尽的案例必须单独列出，不能混入最优率分母。

## 8. 建议的实施顺序

先在内存状态上完成候选传递测试，再改有界枚举；两者通过后再接入预算记账，最后修改实验 runner。每一步都运行对应小图，而不是一次修改所有算法。公共模拟器、Exact 或 schema 发生变化时再运行完整测试，并重新生成受影响的 reference result。

## 9. 结果表字段建议

每行至少包含 benchmark id、类别、hash、算法、seed、makespan、Exact status、gap、preemption count、forced idle、resource utilization、planner decisions、candidate count、constructor operations、eval calls、runtime、fallback reason 和 trace validation。汇总时同时给出算术平均、最大值和分位数；样本不足时明确标注，不计算看似精确的比例。

## 10. 具体任务拆分

任务 C1 修订数据类和返回值，不改变算法分数；完成标志是旧贪心行为不变，其他构造器可以在测试图上返回不同 selected。任务 C2 改为流式有界枚举，完成标志是操作数随上限受控。任务 C3 引入共享预算，完成标志是任何路径都不超过调用上限。任务 C4 扩充结果 schema 和 CLI，完成标志是失败状态可从 JSON 独立判断。任务 C5 重跑全部小图和分类实验。

每项应单独提交测试证据。若 C1 改变旧结果，先解释旧实现为何错误，不为维持旧数字而保留错误路径。若 C2 发现枚举仍可能指数增长，应降低默认上限并允许只用贪心回退。C3 不应通过吞掉异常伪装为完成，所有预算退出都必须保留合法的当前 schedule 或明确失败。

## 11. 验收表

| 验收项 | 方法 | 通过标准 |
|---|---|---|
| 候选传递 | 两候选反例 | selected 与实际 trace 首动作一致 |
| 资源合法 | validator 与手工核对 | 无冲突且包含极大 |
| 枚举上限 | 高冲突组合图 | 生成量不超过上限 |
| 评估预算 | 1、2、3 次边界 | 实际调用不超过配置 |
| 状态报告 | 超时/截断/回退样例 | JSON 状态互相可区分 |
| 结果有效 | Exact 小图 | 仅 optimal 进入最优率 |

## 12. 兼容和迁移

不改 `muti_channel` 公开目录名。旧算法名称可保留别名，但输出增加版本号；旧结果不删除，在新结果说明中标注“候选未实际执行”而停止引用。若 schema 新字段暂时可选，loader 要为旧文件给出明确 legacy 状态，不能默认为成功。

## 13. 预计失败模式

候选爆炸时回退到确定性贪心；评估预算不足时执行已知合法 baseline；Exact 超时时只报告可行值；真实数据资源映射不完整时拒绝进入正式汇总。任何 fallback 都要记录原因，且不能因为 fallback 结果恰好较好就标成完整算法结果。
