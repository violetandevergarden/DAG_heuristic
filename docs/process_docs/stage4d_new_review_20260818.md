# Stage 4d 选择性后续评估审查

## 1. 范围与阶段关系

正式 Stage 4d 研究在少数可能改变后续释放的通信之间进行有限后续评估，以减少全量搜索成本。历史材料中的 `stage4e_selective` 对应本阶段。审查依据阶段计划、公共可抢占语义和当前选择性评估实现。

## 2. 实现和已完成工作

核心代码在 `src/llm_structured/selective_rollout.py` 和单通道复杂链适配器，实验包括 contention census 与 selective rollout evaluation。当前实现能在最长尾基线和一个候选通信之间进行有限深度评估，使用剩余状态、触发条件、时间/调用预算和 fallback；测试覆盖基本合法性与预算回退。45 个已登记单通道复杂 DAG 中，触发且归一化最长尾差距不超过 0.25 的条件下有 7 胜、38 平、0 负，完成评估 134 次；无条件评估仍为 7 胜、38 平、0 负，但调用 350 次。

这些结果说明选择性评估可能减少调用次数，尚不能说明阈值或触发器具有泛化能力。45 个案例同时用于阈值选择和最终报告，没有独立留出集；三个旧的真实派生小案例没有观察到胜利。72 个 LLM census 案例中 0 个完整结束、47 个部分、25 个超时，只有 35 个案例观察到选择差异，证据仍是有界前缀。

## 3. 实现缺陷

`RolloutBudget.rollout_depth` 允许为 0，但 `evaluate_rollout` 把 depth<=1 当作深度 1，配置值与实际行为不一致。`max_candidates` 大于 2 时被接受但没有生效，代码始终只比较最长尾和一个挑战者，配置名称会误导实验。

`heuristic_disagreement` 并没有比较两个完整启发式：挑战者本来就被刻意选成不同于最长尾的第一个通信，因此该信号在有多个 eligible 通信时几乎总为真。`immediate_compute_release` 和 `last_missing_join` 对所有候选使用 `any`，可能因为无关通信满足条件而触发；应只计算基线和候选本身。`ready_set_delta` 实际是 eligible communication 集合变化，不是 ready task 集合变化，名称和文档不一致。

缓存键只有归一化状态和特征版本，但缓存特征含依赖 `previous_eligible` 的 ready_set_delta；同一状态在不同前序集合下会错误复用。时间限制在一次完整最长尾评估后才检查，无法中断单次调用；挑战者评估还可能在超过 expansion limit 后继续完成。总时间也只在触发前检查，不能保证总预算。

当前工作区已有深度二修改，属于用户未提交变化，本审查不改动。现有测试没有覆盖上述边界。实验 runner 使用同一数据集选择阈值和报告结果，每个案例只有一个确定随机种子；resume 会从头重启部分案例，而非从模拟器检查点继续。

## 4. 证据质量与判断

7 胜全部来自同一 45 案例开发集，不能据此声称阶段算法有效；无条件和选择性结果胜负相同，只能说明在这批数据上节省了一部分调用。超时和部分结果没有形成完整的失败分层，也没有真实 R-P/R-S 留出集。完整测试 169 passed 证明回归未破坏已有接口，不证明触发信号正确。

| 项目 | 状态 |
|---|---|
| 复用公共模拟器和合法回退 | 基本完成 |
| 深度、候选数和预算契约 | 未完成 |
| 触发特征的语义准确性 | 未完成 |
| 独立阈值和留出评估 | 未完成 |
| 可用于正式算法结论 | 不具备 |

## 5. 结论

Stage 4d 是有价值的成本控制原型，但目前更像开发期观察工具。应保留 7/38/0 和调用数作为历史开发结果，明确禁止外推；先修正深度、候选、缓存和预算语义，再冻结阈值并使用独立真实派生数据验证。若修正后收益只体现为调用减少而质量不降，可作为其他算法的可选评估层；若质量依赖不真实的触发信号，则应退回特征设计阶段。

## 6. 详细审查表

| 方面 | 当前观察 | 需要留下的证据 |
|---|---|---|
| 触发 | 多个信号可能由无关候选触发 | 每次触发的候选、信号来源和前后状态 |
| 候选 | 实际只比较 LT 与一个挑战者 | 候选排序、截断位置、候选数 |
| 深度 | 0 与 1 等价 | 配置值和实际展开层数 |
| 预算 | 完整调用后才检查 | 每次调用前后计数及超限原因 |
| 缓存 | 未包含前序 eligible 集合 | 命中键和特征摘要 |
| 数据 | 阈值选择与报告同集 | 开发/留出清单和 hash |

这些字段应进入机器可读结果，而不是只写在实验日志中。否则出现退化时无法区分触发错误、候选错误和评估预算不足。

## 7. 按模块审查

结构特征模块把多种信号压成触发布尔值，便于运行，但不利于判断误触发。应保留每项原始值以及最终规则。单通道适配器目前能把 selected action 交给公共模拟器，这一点正确；它不应复制依赖释放或通信剩余量更新。

评估器的职责应是“在给定候选与预算下返回可比较的估计”，而不是隐式改变候选数和深度。当前 depth=0、max_candidates>2 的行为违背这一契约。实验 runner 又把开发和评价放在同一批数据中，使实现问题和统计问题叠加。

## 8. 触发信号逐项判断

最长尾 margin 是可保留的连续量，但要处理分母为零和并列。启发式分歧只有在两个完整排序器首选不同时才有意义。立即释放计算应比较候选完成后新增 ready 的 compute；最后缺失 join 应限定为候选是否是某个 join 的唯一未完成前驱。eligible 集合变化应从前一决策时刻到当前时刻计算，并进入缓存键。

这些信号都只是“值得评估”的提示，不是 makespan 收益证明。触发成功率应分为触发后改善、持平、退化和预算回退四类。

## 9. 最小反例与边界

需要一个第三候选触发 join、但 LT 与挑战者都无该性质的图，复现当前 `any` 误触发；一个相同归一化状态由不同 previous eligible 到达的图，复现缓存污染；一个最大调用数为 1、两个候选均需 completion 的图，复现超预算；一个 depth=0 的图，验证完全不进行 rollout。

## 10. 对历史数字的限定

134 与 350 是 completion call 数，不等同于节点展开、模拟事件或墙钟时间。7 胜没有独立复验，38 平中也可能存在不同 trace。72-case census 的 0 completed 表明它只能描述已观察前缀，不能估计完整图的选择状态分布。后续文档引用这些数字时必须带上数据范围和完成状态。

## 11. 完成条件对照

计划所要求的“识别少数高价值决策”目前只在开发集观察到，尚未由独立数据确认；“节省预算”只按 completion call 计量，尚未按墙钟和节点展开复核；“把节省预算用于更深或更宽搜索”尚未形成公平实验。合法轨迹和稳定回退已具备，是后续修正可以依赖的部分。

审查建议把阶段状态记为“原型可运行，触发与预算契约待修正，真实验证未完成”。不能记为已完成，也不需要推倒重来。现有 45 例、72 例前缀和三个旧真实派生样例都应保留原始结果，重跑时生成新版本而非覆盖。

## 12. 结果审计注意事项

每次 rollout 的基线和挑战者必须从同一决策状态复制，不能共享被修改的 runtime；两条完成模拟必须使用同一 fallback 和 tie-break。若候选估计相同，应稳定选择基线以减少不必要差异。随机种子只影响明确的随机候选，不应影响公共模拟器事件顺序。

对 timeout 案例应保存已完成决策数、最后时刻、最后 eligible 集合和预算消耗，便于恢复和分层。只保存“timeout”无法判断是图规模、候选爆炸还是单次 completion 过慢。
