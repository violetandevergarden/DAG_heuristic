# Stage 4c 代码修正与验证建议

## 1. 修正目标

本方案针对 `stage4c_code_review_20260821.md` 发现的问题。目标是先保证候选确实可被选择、所有预算是可验证的硬边界，再建立小图真值和真实分层证据。不得为保留历史数字而维持错误契约，也不要同时重构公共模拟器或无关不可抢占代码。

## 2. P0：先修正执行契约和预算

### 2.1 分开“基线、候选和最终选择”

修改 `PackingResult`，至少明确保存：

- `baseline`：确定性 LT 贪心动作；
- `candidates`：去重后的合法极大集合；
- `selected`：按当前选择器最终决定执行的动作；
- `constructor`、`selector` 和配置版本；
- `truncated`、`fallback_reason` 与完整统计。

构造器只负责产生 baseline 和 candidates，不应假装已经完成质量选择。调度器必须显式配置选择器，例如 `baseline`、`set_score` 或 `depth1_completion`。若选择器为 baseline，则算法名称也应如实标记为候选覆盖诊断，不能命名成“交换算法”。

验收：在已知两个极大动作 makespan 不同的小图上，最终 trace 首动作必须等于 `selected`；关闭 rollout 时，集合评分选择器也能够执行非 baseline 候选。

### 2.2 将极大集合枚举改为流式有界生成

禁止 `model.maximal_actions(state)` 全量返回后再切片。增加能够逐个产生极大集合的回溯接口，接受：

- 最大集合数；
- 最大构造操作数；
- 截止时间；
- 可选内存或递归节点上限。

每产生一个候选立即去重、验证并累计；到任一上限立即停止，返回 `truncated=true`。baseline 始终单独保留，不占“额外候选”配额。`max_sets=0` 统一定义为不生成额外候选；负值继续报错。

验收：构造一个极大集合数量很多的小冲突图，设上限为 2，断言实际生成数不超过 2，访问节点数受限，且没有调用全量 `maximal_actions`。

### 2.3 建立共享预算记账器

为一次决策创建单一预算对象，统一记录和检查：

- 构造操作数；
- 生成和保留候选数；
- 完成模拟调用数；
- 单决策截止时间；
- 整图截止时间；
- 可选状态数和内存上限。

每次候选完成模拟前先占用一次调用额度；额度不足就停止，不能一次函数调用批量超过 `b_eval`。候选构造、集合评分和完成模拟都使用同一截止时间。若完整模拟不能中途安全停止，应只在有足够调用额度时启动，并在进程级墙钟保护下运行。

验收：分别设置 `b_eval=0/1/2`，任何路径的 `completion_calls` 都不得超过配置；墙钟耗尽时执行已验证的 baseline，并记录准确原因。

### 2.4 统一 fallback 和状态字段

每个决策保存：`status`、`constructor_status`、`selector_status`、`candidate_count`、`eval_calls`、`operations`、`runtime_ms`、`fallback_reason`。整图汇总保存各原因计数，不把原因压成一个最终字符串。

将 `planner_triggered` 改为实际触发次数；另保留 `planner_decisions` 表示总决策数。`evaluated_candidates` 只统计真正执行过集合评分或完成模拟的候选，生成数量另用 `generated_candidates`。

## 3. P1：补齐正确性和小图真值

### 3.1 动作与事件边界测试

增加以下最小测试：

- 团冲突退化为单通信动作；
- 空冲突图唯一动作包含全部通信；
- 极大但非最大数量的动作仍合法；
- 非极大动作由公共模拟器拒绝，不被算法静默补救；
- 通信暂停恢复后的剩余工作守恒；
- 同时完成和零时长 compute 闭包后再计算 eligible；
- 没有 eligible 时仅 forced idle，不产生 WAIT；
- 相同输入、状态、配置和 seed 返回相同结果；
- 构造前后状态完全相等。

### 3.2 全部极大首动作与 Exact 对拍

对随机小资源图和攻击图：

1. 用独立小图枚举器列出全部极大集合；
2. 与模拟器合法动作集合交叉核对；
3. 对每个首动作执行未压缩 Exact 后续求值；
4. 保存全部并列最优首动作，而不是单一标签；
5. 分别计算候选覆盖率、选择命中率和最终 optimal rate。

未完成 Exact 必须标为 feasible/time_limit/state_limit，不进入最优率分母。

### 3.3 补齐单目标反例

保留现有六个 motif，并至少补充：

- 相同冲突图、不同下游 DAG 的成对样例；
- 共享下游导致逐顶点求和重复计分；
- 热点资源高但不在最终关键路径；
- 频繁抢占增加区间却不改善 makespan；
- 极大集合大小不同但较小集合长期更优；
- 候选已覆盖最优动作但评分选错的样例。

每个 motif 只隔离一个机制，并保存手工解释、全部首动作值和 trace。

## 4. P1：修正实验入口和结果契约

### 4.1 迁移正式编号

将实验说明和新输出 schema 改为 Stage 4c，例如 `stage4c-packing-v2`。旧 `stage4f-packing-v1` 结果保留为历史，不覆盖，并注明“非 rollout 高级构造器实际执行 baseline”。公共目录 `muti_channel` 不改名。

修正实验启动方式，使按仓库文档安装后可以直接运行；若必须依赖 editable install，应在命令和失败信息中明确说明，不依赖临时设置 `PYTHONPATH`。

### 4.2 结果字段

每行至少保存：

- benchmark id、内容 hash、类别和来源；
- manifest 版本、转换状态、竞争证据等级；
- workload、topology、DP/TP/PP、任务数和资源数；
- 算法、顶点评分、构造器、集合评分、seed、完整预算配置；
- status、timeout、fallback 次数和逐原因计数；
- makespan、相对 FIFO/LT 变化、Exact 状态和 gap；
- 候选生成数、覆盖率、评价数、交换数、操作数；
- 决策数、策略分歧数、集合大小分布；
- 抢占数、通信区间数、forced-idle、总体及逐资源利用率；
- 构造、评分、模拟和总 wall-clock；
- 峰值内存、trace hash 和验证状态；
- 代码版本、Python 与机器环境。

### 4.3 严格超时

对真实完整回放使用进程级墙钟限制，父进程负责标记 timeout 并保留已知输入和配置。不要依赖仅在外层循环检查的协作式超时。超时样例留在汇总分母中，不用 fallback 的 makespan冒充候选算法完整结果。

## 5. P2：建立符合 Stage 4a 边界的数据分层

### 5.1 固定 Stage 4c manifest

从 Stage 4a 活动 manifest 派生只读的 Stage 4c 实验清单，不修改原 benchmark。每个样例同时记录：

- 转换有效、固定资源映射明确、trace 可回放；
- 竞争证据是完整、认证、有界观察还是 sampled prefix；
- 集合唯一、集合可选、策略分歧、收益敏感或未知；
- 小、中、大规模层；
- 开发集或 holdout；
- workload、topology 和并行配置分层。

只把已观察或认证存在多个极大集合的样例用于主要质量比较；唯一集合用于回归；未知样例只用于成本或继续审计，不能稀释收益统计。

### 5.2 真实 census

先运行低成本 census，逐决策记录 eligible 数、冲突边与密度、连通分量、最大度、资源脚印、多资源通信比例、极大集合数量或下界、简单策略分歧及证据等级。完整枚举不可行时明确写成下界或预算内观察。

从 census 中选择：

- 小型 real-derived slice：可做全部首动作 Exact；
- 中型真实图：所有对照能在统一预算内完成；
- 大型真实图：只做单位决策成本、前缀和内存压力。

## 6. P2：按正交层次运行实验

### 6.1 基线齐全

统一实现并比较固定顺序、FIFO、Longest Tail 和固定 seed 随机顺序补全。所有方法使用相同补全规则并保证集合极大。之后才加入多起点、一次交换、有界枚举和集合评分。

### 6.2 分离构造与评分

按以下顺序实验，每次只改变一个因素：

1. 固定 LT 顶点评分和 baseline 选择器，比较候选覆盖率；
2. 固定同一候选集合，比较顶点聚合、下游并集和浅层完成评分；
3. 固定评分，比较单起点、多起点和一次交换；
4. 比较有无热点、LLM role 和正确 residual 特征；
5. 相同候选数比较直接评分和浅层完成；
6. 相同墙钟比较更宽候选和更深评价；
7. 单独报告 rollout 带来的收益，不能归因于纯 packing。

### 6.3 holdout 与负面结果

预算和阈值只在开发集选择，冻结后在未参与设计的 workload/topology holdout 上运行一次。报告平均、中位、分位数、最坏退化、超时、fallback 和逐样例结果。若复杂方法没有稳定净收益，应形成“LT 足够”或“仅在某类冲突形状有效”的受限结论，不继续堆叠算法。

## 7. 推荐实施顺序

1. C1：修订 `PackingResult` 和显式 selector，增加 selected 与 trace 一致测试；
2. C2：实现流式有界枚举，删除先全量枚举再切片的路径；
3. C3：引入共享预算记账和进程级整图超时；
4. C4：完善统计、fallback 原因和 Stage 4c v2 结果 schema；
5. C5：建立随机小图与全部首动作 Exact 真值；
6. C6：冻结 Stage 4c manifest，完成真实 census 与分层；
7. C7：运行基线、构造、评分、预算消融和真实 holdout；
8. C8：形成适用范围、成本和失败案例结论，决定是否进入 Stage 4g。

每步只修改最小必要模块并先运行定向测试；修改公共模拟器、Exact、schema 或 benchmark 语义时再运行完整测试并重生成受影响结果。

## 8. 再验收标准

| 验收项 | 通过标准 |
|---|---|
| 候选传递 | `selected` 与 trace 实际首动作及后续动作逐次一致 |
| 构造器比较 | 非 baseline 名称对应真实不同选择，或明确标为仅候选覆盖诊断 |
| 枚举硬上限 | 生成过程本身不超过集合、操作和时间上限 |
| 评价硬上限 | 任意配置下 `completion_calls <= b_eval` |
| fallback | 每次原因可追踪，回退动作合法且不伪装成高级方法完成 |
| 小图真值 | 全部极大首动作与独立枚举、未压缩 Exact 一致 |
| Stage 4a 准入 | 正式真实样例具有可核查的转换和竞争证据等级 |
| 公平基线 | 固定顺序、FIFO、LT、随机与候选使用统一输入、预算和补全规则 |
| 结果完整 | 质量、完整率、成本、抢占、forced idle、利用率和内存同时报告 |
| holdout | 参数冻结，保留超时、fallback 和最坏退化 |
| 阶段结论 | 能回答复杂 packing 是否值得，以及明确适用范围或否定结论 |

在这些条件全部满足前，Stage 4c 保持“开发中”，其高级构造器不应作为已验证组件进入 Stage 4g。
